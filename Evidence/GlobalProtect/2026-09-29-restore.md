# GlobalProtect restore regression and repair

Authorized live investigation on September 29 UTC (September 28 local), on
macOS 26.6.2 (25G83), arm64, GlobalProtect 6.3.3-1121, TaskScope 1.0.0 (3).

The user reported a window stuck retrieving portal configuration, then a
duplicate-instance alert during recovery. At first inspection, GlobalProtect's
UI was running but PanGPS was absent. Both user-job overrides were enabled,
but neither user job was loaded; the separate system daemon remained disabled.
This is the state the previous Keep Off toggle-off action could leave: it only
enabled jobs without starting them.

The old Open path restored the VPN service, but loading `pangpa` over an
already-open UI produced another instance. Two GlobalProtect UI processes and
one PanGPS were observed. The duplicate UI job was unloaded, the old UI closed,
and a single UI started against the restored service. The VPN reached Connected.
[Initial service-restoration record](2026-09-29-restore/initial-recovery.json)
captures the missing-service state and its restoration before the later
duplicate alert appeared.

## Changes

- Turning Keep Off off submits the same complete restore command as Open.
- If Open finds the UI running without PanGPS, it unloads only the fixed
  `pangpa` UI job, closes that orphaned UI, and verifies absence before restoring
  the service and app. It never unloads `pangps` or `pangpsd` for UI recovery.
- Before loading an absent `pangpa` job, a fresh inventory, current-user
  ownership, and kernel executable path detect a directly opened UI. The job
  stays unloaded rather than launching a duplicate. Unknown inventory fails.
- The on-screen help and support documentation describe full restoration.

## Installed build and live checks

Final installed executable SHA-256:
`3538324909db4badb0c6d75889746f9a446bef2325b75d008ae55c60b8fc164d`.

1. [Open while connected](2026-09-29-restore/healthy-open.json): GlobalProtect
   stayed Connected. The UI and PanGPS PIDs were unchanged, with one UI process
   throughout the observation and no administrator window.
2. [Quit All](2026-09-29-restore/stop.json): automatic disconnect and full stop
   completed. All known jobs were disabled/unloaded and all vendor processes
   absent. TaskScope's menu-bar frame remained unchanged.
3. [Turn Keep Off off](2026-09-29-restore/toggle-restore.json): the actual switch
   restored both session jobs and exactly one UI plus PanGPS, without an
   administrator window. It no longer left enabled-but-unloaded jobs behind.
4. [Final state](2026-09-29-restore/final-connected.json): Connected, one UI,
   one PanGPS, no duplicate alert, both session jobs enabled/loaded, unused
   system daemon disabled/unloaded. Public GitHub HTTPS returned 200. Vendor
   launch plists remained unchanged. The VPN was left connected.

An additional attempt to recreate the orphaned UI on the final build was
aborted: manual Disconnect requests did not produce the required consecutive
Not Connected observations. The test guard made no launchd changes in those
attempts. No policy explanation is inferred. Orphan recovery and the case of a
healthy UI opened outside its launch job are covered by deterministic tests;
those exact branches were not reproduced live on the final binary.

## Automated validation and limits

471 tests passed, one opt-in test skipped, zero failures. Coverage and strict
concurrency/actor-check runs passed. Warnings-as-errors debug build, release
build, packaging tests (including 106 release-evidence cases), shell syntax,
and diff checks passed. New cases cover orphan UI recovery without unloading
VPN jobs, failed UI unload/exit, existing direct UI, missing inventory,
impostor/other-user processes, and the actual toggle-off restore command.

Other GlobalProtect versions, managed-policy behavior, private-resource
reachability, logout/reboot, and pre-login remain outside this evidence. The
broader compatibility release gate remains unverified.
